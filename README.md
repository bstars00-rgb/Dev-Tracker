# OHMY Integration Tracker

한 페이지짜리 **읽기 전용** API 연동 현황 화면. 엑셀이 원본이고, 이 화면은 그걸 보기 좋게 보여줄 뿐입니다.

- 로그인 없음, 데이터베이스 없음, 서버 없음
- `index.html` 더블클릭하면 바로 열림 (인터넷 연결도 불필요)
- GitHub Pages로 자동 배포 — 팀은 링크 하나만 있으면 됩니다

**링크:** https://bstars00-rgb.github.io/Integration-Tracker/

---

## 업데이트 (엑셀이 원본)

### 방법 A — 엑셀만 바꿔서 푸시 (권장)

1. `data/Dev_Schedule.xlsx` 를 최신 파일로 교체 — **파일명은 그대로**
2. 커밋 & 푸시

GitHub Actions가 변환하고 배포합니다. **Node.js 설치 필요 없습니다.**
1~2분 뒤 링크에 반영됩니다. 진행 상황은 저장소 **Actions** 탭에서 볼 수 있습니다.

### 방법 B — 올리기 전에 로컬에서 확인

1. `data/Dev_Schedule.xlsx` 교체
2. **`update.bat` 더블클릭** → 변환되고 화면이 자동으로 열림
3. 확인되면 커밋 & 푸시

이 방법은 Node.js가 필요합니다 ([nodejs.org](https://nodejs.org) LTS). `update.bat` 이 첫 실행 때 안내합니다.

> **엑셀 규칙:** 파일명 `Dev_Schedule.xlsx`, 시트명 `Dev Tracker`, 헤더 3행.
> 컬럼명이 바뀌면 [`scripts/build.mjs`](scripts/build.mjs) 맨 위 목록만 고치면 됩니다.
> 시트가 깨지면 Actions가 배포를 막고 에러로 알려줍니다.

## 주간 갱신 (로컬 실행)

원본은 **`Desktop/REPORT/3. CRM/`** 에 매주 토요일 자동으로 내려오는 Dev Schedule 워크북입니다.
그 폴더를 채우는 건 기존 파이프라인(Device Code 위임 인증)이고, 이 보드는 **받아둔 파일을 읽기만** 합니다.
여기서 SharePoint 인증을 따로 하지 않습니다.

```bash
npm run weekly
```

`3. CRM/` 에서 최신 워크북을 알아서 찾습니다 (`_latest_` 접두 파일 우선, 없으면 수정시각 최신).
복사 → 변환 → 검증 → 변경이 있을 때만 커밋·푸시까지 한 번에 끝납니다.

경로를 직접 주려면:

```bash
npm run weekly -- --source "C:/path/to/Dev_Schedule.xlsx"
```

기존 주간 파이프라인(`run-weekly.js` 등)에 한 줄로 붙일 수 있습니다:

```js
execSync('npm run weekly', {
  cwd: 'C:/Users/LENOVO/Desktop/AI Dev Tracker/board',
  stdio: 'inherit',
});
```

### 읽는 시트

| | |
|---|---|
| 시트명 | `Dev Tracker (IT)` (없으면 옛 이름 `Dev Tracker` 로 폴백) |
| 헤더 | 3행 |
| 마일스톤 | 12단계 — ① 미팅/1st Contact (10%) ~ ⑫ API Live 완료 (100%) |

컬럼은 **이름으로** 찾습니다. 순서가 바뀌어도 동작하고, 이름이 바뀌면
[`scripts/build.mjs`](scripts/build.mjs) 상단 `COLUMNS` 목록만 고치면 됩니다.

시트가 이미 계산해 둔 값(`현재 단계`, `다음 게이트`, `개발 주체`, `연동 방향`, `Status vs 날짜 정합성`)은
그대로 읽어 씁니다. **다시 계산하는 건 경과일 하나뿐입니다** — 시트의 `경과일` 은 저장하는 순간부터 낡기 때문입니다.

### 안전장치

- 1KB 미만이거나 zip이 아닌 파일(로그인 페이지 등)은 덮어쓰지 않고 중단
- 파싱 결과가 0행이면 **커밋 전에** 중단
- 변경 없으면 빈 커밋을 만들지 않음
- `--no-push` 로 커밋·푸시 없이 결과만 확인
- Biz Impact 미기재, Status 불일치 건수를 빌드 로그에 경고로 출력

## 화면 구성

우측 상단 **한국어 / English** 로 전환됩니다. 선택은 브라우저에 저장되고, 처음 방문이면 브라우저 언어를 따릅니다.
파트너명·Status·Category 같은 시트 값은 원본 그대로 두고 인터페이스만 번역합니다.

### Dashboard 탭

**카드 9장** — 값 · 전체 대비 비중 · 구성 막대 · 한 줄 해설. 클릭하면 해당 조건으로 필터된 목록으로 넘어갑니다.

| 카드 | 뜻 | 해설에 뜨는 것 |
|---|---|---|
| 전체 | 시트 전체 | 최다 상태와 건수 |
| High Impact | **매출·물량 기여가 큰 건** (리스크 아님) | 미착수 / 진행 중 / 완료 분해 |
| 완료 (Live) | 라이브 완료 | 단계 날짜로 계산한 평균 소요일 |
| 개발 착수 대기 | SLA 완료 ~ 킥오프 예정 | OHMY 직접 / 파트너 / 스위칭 분해 |
| 개발 진행 중 | 구현 ~ 오픈 준비 | 같음 |
| 스위칭 경유 | TGX·SHIJI 등 경유 | 플랫폼별 건수 |
| OHMY 공수 Full | 우리가 100% 붙는 건 | 그중 진행 중 건수 |
| 손이 필요함 | 방치·무기록 | 가장 오래 조용한 건 |
| 90일+ 방치 | 3개월 이상 | 최장기 건 |

### 공수 × 임팩트 4분면

OHMY 개발 공수(시트의 `OHMY Dev Load`)와 매출·물량 기여(`Biz Impact`)를 교차한 분류입니다.
상자를 클릭하면 그 분류만 목록으로 넘어갑니다.

| | 임팩트 **강함** | 임팩트 **약함** |
|---|---|---|
| **공수 적음** | **즉시 착수** — 적게 넣고 크게 먹는 건. 최우선 | **여유 시 처리** — 부담 없지만 급하지도 않음 |
| **공수 많음** | **전략 투자** — 할 가치 있음. 일정·인력 사전 배정 | **근거 필요** — 공수는 큰데 기대 효과가 안 보임 |

`근거 필요`를 "하지 말 것"으로 하지 않은 이유: 전략적으로 해야 하는 경우가 실제로 있습니다.
못 박는 대신 **진행하려면 이유를 대라**는 요구로 두는 게 의사결정에 쓰입니다.

판정 기준: 공수 많음 = `Full` 또는 `Half` · 임팩트 강함 = `High`.
**`Mid`와 빈칸은 모두 "약함"으로 갑니다.** 지금 108건 중 93건이 Impact 미기재라
`근거 필요` 26건 상당수는 실제로는 그냥 미기재일 수 있습니다 — 패널 아래에 그 사실을 명시해 뒀습니다.
시트의 Biz Impact를 채우는 게 이 화면을 가장 크게 개선하는 방법입니다.

### 개발팀 관점 · 지금 할 일

대시보드의 핵심 패널입니다. **현재 단계 × OHMY 개발 공수 × 스위칭 경로**를 조합해 다음 액션을 뽑습니다.

**구현 경로 판정**

| 조건 | 경로 | 뜻 |
|---|---|---|
| Switching 값이 있음 | `{플랫폼} 경유` | 커넥터 설정 — OHMY가 코드를 짜지 않음 |
| OHMY Dev Load = Full / Half | `OHMY 직접` | 우리가 구현 |
| 그 외 (Minimal / None) | `파트너 구현` | 파트너가 우리 API에 붙음. 우리는 키·스펙·질의 대응 |

**단계별 다음 액션**은 사내 API 연동 프로세스 9단계를 그대로 따릅니다.

| 진행률 | 다음 할 일 | 담당 |
|---|---|---|
| 0% Contact | 계정 발급 · Top-Selling 리스트 · 3~6주 Follow-up | GSM |
| 20% NDA | 적합성 5문항 (채널·B2B 비중·일 주문량·공급방식·통화) | GSM |
| 30% Contract | Deposit·Credit Ratio·Settlement·Currency 합의 → 승인 | SLA |
| 40% SLA | **DEV Credential 발급 · API SPEC · DEV 환경 URL** | 개발 |
| 45% Kickoff | 고객사 IT 명단·IP 확보 → Teams 채널 개설 | 개발 |
| 50% Dev Kickoff | 테스트 시나리오 배포 · Certification · Static 갱신 | 경로에 따름 |
| 60% Certification | Cert 문서·Log 검증 → Pass 판정 | 경로에 따름 |
| 70% Live Test | **라이브키 발급** → 실거래 부킹 검증 | 개발 |
| 75% Dev 완료 | 부킹 기록 확인 · Go-Live D-Day 통보 | 개발 |
| 80% Live Open | D-7 모니터링 시프트 · D-Day 대기 | 개발 |
| 90% First Booking | 에러율·취소율 모니터링 · 주간 데이터 공유 | 개발 |

**키 발급(40·45·70·75)과 런칭 모니터링은 구현 주체와 무관하게 항상 OHMY 개발팀**입니다. 구현(50·60)만 경로를 따릅니다.
60~70% 구간에는 **라이브키는 Cert Pass + Deposit 입금 둘 다 충족해야 발급**이라는 게이트가 함께 표시됩니다.

**개발 대응 주체 컬럼** — "담당자가 누구냐"가 아니라 **어느 팀 개발이, 어느 강도로 붙어 있어야 하는가**를 표시합니다.
세일즈는 어차피 전 건을 보고 있으니, 개발 기준으로만 눈금을 매겼습니다.

| 표시 | 뜻 | 언제 |
|---|---|---|
| **OMH 개발** (빨강) | OMH 개발팀이 직접 코드를 씀 | 50 중 OHMY 직접 · 40·45·60·70·75·80·90 중 OHMY 직접 |
| **OMH 지원** (주황) | 구현은 상대가 하지만 **OMH가 산출물을 내야 함** — DEV 키·인증 판정·라이브키·모니터링 | 40·45·60·70·75·80·90 중 파트너/스위칭 |
| **스위칭 검수** (주황 테두리) | 스위칭 플랫폼이 커넥터를 붙이고 OMH가 검수 | 50 중 스위칭 경유 |
| **파트너 개발** (파랑 테두리) | 파트너가 코드를 씀. OMH는 기술 질의 대응 | 50 중 파트너 구현 |
| **개발 사전 인지** (보라 테두리) | 아직 영업 단계지만 **공수 큰 건이 오고 있음** | 0·20·30 중 Dev Load Full/Half 또는 High Impact |
| 영업 단계 (회색) | 개발 관여 없음 | 그 외 |

맨 위 두 줄이 이 컬럼을 만든 이유입니다. Klook은 **OMH 개발**(우리가 코드를 씀), Gotadi는 **OMH 지원**
(파트너가 코드를 쓰고 우리는 DEV 키를 발급)입니다. 예전에는 둘 다 "개발 대응"으로 똑같이 보여서
어느 쪽 개발이 움직여야 하는지 구분이 안 됐습니다.

`개발 사전 인지`가 "개발팀이 좀 더 신경 쓰라"는 장치입니다. 계약이 끝나고 나서야 알게 되는 대신,
공수가 큰 High Impact 건이 아직 접촉 단계일 때부터 목록에 뜹니다.

패널 상단에 `OMH 개발 N · OMH 지원 M · 스위칭 검수 K · 파트너 개발 L · 사전 인지 P` 요약이 뜨고,
`전체 / OMH 개발 필요` 토글로 **OMH 개발·지원·스위칭 검수** 건만 추릴 수 있습니다.
파트너 개발 건은 파트너가 굴리는 것이므로 이 토글에서 빠집니다.

### 나머지 패널

**PIC별 부하** · **카테고리별 현황** · **마지막 활동 경과** · **지금 손봐야 할 10건** — 전부 클릭하면 목록으로 드릴다운됩니다.

### 전체 목록 탭

| | |
|---|---|
| 검색 | 파트너·PIC·카테고리·단계 검색. `/` 키로 포커스, `Esc` 로 해제 |
| 필터 | 상태 · 카테고리 · PIC · **현재 단계** · 활동상태 조합 가능 |
| 정렬 | 컬럼 헤더 클릭 |
| Stage track | 11단계를 칸으로 표시 — 채워진 칸이 날짜가 기록된 단계, 마우스 올리면 날짜 |
| 행 클릭 | 11단계 날짜 전체 펼쳐보기 |
| CSV 내보내기 | 지금 화면에 보이는 것만 (엑셀에서 바로 열림) |

**기본 정렬은 "손이 필요한 순"입니다.** 90일+ 방치 → 30일+ → 14일+ → 기록없음 → 정상 → Live 순으로,
같은 그룹 안에서는 진행률이 높은 것부터. 이미 Live인 건은 오래됐어도 맨 아래로 갑니다 — 멈춘 게 아니라 끝난 것이니까요.

**경과일은 엑셀 값을 쓰지 않고 오늘 기준으로 다시 계산합니다.** 시트의 `Days Elapsed` 가 낡아도 화면은 항상 정확합니다.

색: 14일 이내 회색 · 15~30일 주황 · 31~90일 진한 주황 · 90일 초과 빨강 · 활동기록 없음 빨강 · Live 초록.
다크모드는 OS 설정을 따라갑니다. 탭 상태는 주소창 `#dashboard` / `#list` 로 남아서 링크 공유가 됩니다.

## 시트에 추가하면 자동으로 켜지는 컬럼

보드는 아래 컬럼을 **이름으로** 찾습니다. `Dev Tracker` 시트 3행(헤더)에 추가하기만 하면
다음 빌드부터 화면에 나타납니다. 코드 수정은 필요 없습니다.

| 추가할 헤더 | 채우는 값 | 켜지는 것 |
|---|---|---|
| `목표 오픈일` 또는 `Target Go-Live` | 날짜 | 목표 오픈 컬럼 · D-day · 지연 일수. 라이브 이후에는 실제 오픈일 대비로 고정 |
| `현재 블로커 / 이슈` 또는 `Blocker` | 자유 텍스트 | 목록의 `BLOCKER` 배지, 상세 행의 블로커 줄 |
| `비고` | 자유 텍스트 | 상세 행의 비고 |
| `Status vs 날짜 정합성` | `OK` / 불일치 사유 | 대시보드 정합성 카드 |

**Status 값 추가** — `Status` 데이터 유효성 목록에 `On Hold`, `Dropped`를 넣으면
해당 행은 진행 파이프라인에서 빠지고(`현재 담당`이 보류/드롭으로 바뀜) 별도로 필터할 수 있습니다.
지금은 상태값이 전진 방향뿐이라, 멈춘 건과 아직 시작 안 한 건이 구분되지 않습니다.

없는 컬럼은 대시보드 하단 `유형별 단계 기록률` 패널 아래에 그대로 적어둡니다.
빈 칸이 "문제 없음"으로 읽히지 않게 하려는 것입니다.

### 목표 오픈일이 없을 때

`⑧ Dev Completion Planned (75%)` 날짜를 대신 씁니다. 시트에서 유일하게 앞을 내다보는 날짜라서인데,

## 유형별 단계 기록률

진행률을 유형끼리 비교하려면 먼저 유형별로 단계가 기록돼야 합니다. 지금 시트는 그렇지 않습니다.

| 유형 | 행 | 단계 날짜가 있는 행 | 쓰인 단계 |
|---|---|---|---|
| Channel API | 79 | 46 | 11/11 |
| 3rd Party Hotel | 13 | 1 | 1/11 |
| Switching System | 7 | **0** | 0/11 |
| 3rd Party Activity | 3 | **0** | 0/11 |
| CRS | 2 | **0** | 0/11 |

즉 11단계 퍼널은 사실상 Channel API 전용이고, 나머지 25건의 진행률은 Status에서만 나옵니다.
CRS가 0%인 것은 뒤처져서가 아니라 **추적되지 않아서**입니다. 이 구분을 패널에 그대로 표시합니다.

유형별로 해당 없는 단계를 N/A 처리하고 분모를 다시 잡는 방식은, 유형마다 어느 단계가 N/A인지
팀이 정해주면 반영할 수 있습니다. 데이터로는 추정할 수 없습니다 — 위 세 유형은 기록 자체가 없습니다.

## Teams 인사이트 메시지

```bash
npm run teams          # output/ 에 3개 HTML 생성, 발송은 안 함
```

진행중 건만 봅니다. 라이브는 끝난 일이고 미착수는 주간 안건이 아니라서,
둘 중 하나라도 넣으면 실제로 움직인 10여 건이 묻힙니다.

| 채널 | 언어 | 담는 것 |
|---|---|---|
| `IT × GSM + Contents` | 영문 | OMH 개발이 산출물을 내야 하는 건만 (지금 4건) |
| `Global Sales Team` | 국문 | 45일+ 정체 건을 PIC별로 묶은 알럿 |
| `Global SCM Director` | 국문 | 정체 규모 + 판단이 필요한 건 |

정체 기준은 `scripts/teams-msg.mjs` 의 `STALE_DAYS` (현재 45일).

세일즈 알럿은 **PIC별로 묶습니다.** 알럿은 "누구 건인지"가 먼저여야 움직입니다.
리더 메시지는 정체 목록을 날짜순이 아니라 **진행률순**으로 냅니다 —
날짜순으로 뽑으면 20%에서 죽은 건이 맨 위로 올라오는데, 정작 비용이 큰 것은
많이 갔다가 멈춘 건입니다.

발송은 별도 단계라, 보내기 전에 읽어볼 수 있습니다.

```bash
node scripts/post-teams.js msg "Global Sales Team" "<파일>"          # dry run
node scripts/post-teams.js msg "Global Sales Team" "<파일>" --send   # 실제 발송
```

주간보고 파이프라인에서는 `run-weekly.js` Step 6.6 이 생성과 발송을 함께 합니다.

## 파일 구성

```
index.html            화면 구조
styles.css            스타일
app.js                필터 · 정렬 · 검색 · CSV
data/
  Dev_Schedule.xlsx   ← 원본. 이것만 교체하면 됨
  tracker.js          자동 생성 — 화면이 읽는 파일
  tracker.json        자동 생성 — 다른 도구에서 쓸 원본 데이터
i18n.js               한국어 / English 문구
scripts/build.mjs     엑셀 → JSON 변환기
scripts/serve.mjs     로컬 미리보기 (npm run preview)
update.bat            더블클릭용
```

`tracker.js` / `tracker.json` 은 자동 생성물이지만 **커밋해 두세요.** 그래야 clone 하거나
폴더를 복사한 사람이 아무것도 실행하지 않고 바로 볼 수 있습니다.
